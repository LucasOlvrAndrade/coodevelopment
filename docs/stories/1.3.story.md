## Story

**As a** usuário,
**I want** buscar alguém pelo usuário do GitHub e mandar um pedido de amizade,
**so that** eu possa chamar essa pessoa para uma jam.

## Acceptance Criteria

1. A busca encontra quem já tem conta no app pelo usuário do GitHub.
2. Enviar pedido cria um pedido pendente visível para os dois.
3. Quem recebe aceita ou recusa; aceitar cria a amizade (FR2).
4. Qualquer um dos dois desfaz a amizade.
5. Não é possível pedir amizade a si mesmo nem duplicar pedido.

## Dev Notes

### Previous Story Insights

- `exigirSessao()` já existe em `src/servidor/auth.ts` (lança `ErroApp("sem_sessao", 401)`); `obterSessao()` lê cookies e precisa ficar dentro de `Suspense` (`cacheComponents`).
- O driver é `drizzle-orm/neon-http`: sem `db.transaction` interativo. O adaptador do Better Auth não usa transação no Postgres (conferido na 1.2).
- `user.login` não é único de propósito: no GitHub, um nome trocado fica livre para outra pessoa antes de o dono antigo entrar de novo e atualizar o dele. O estável é `github_id`. A busca pode trazer duas pessoas com o mesmo login; a tela mostra as duas, com nome e foto.
- Renderizar uma página inteira com componentes assíncronos de servidor no Vitest trava atualizações de estado (achado no design da página inicial): testar componentes cliente diretamente.
- `pnpm` roda direto nesta máquina (shim do corepack em `C:\Users\User\bin`); o `next dev` às vezes perde uma edição de CSS: se o visual não bater com o arquivo, reiniciar o servidor.

### Modelo de dados

[Source: architecture/data-models.md#amizade-e-pedidoamizade, architecture/database-schema.md]

```sql
create table pedido_amizade (
  id text primary key,
  de text not null references "user"(id) on delete cascade,
  para text not null references "user"(id) on delete cascade,
  status text not null default 'pendente' check (status in ('pendente','recusado')),
  criado_em timestamptz not null default now(),
  check (de <> para),
  unique (de, para)
);

create table amizade (
  usuario_a text not null references "user"(id) on delete cascade,
  usuario_b text not null references "user"(id) on delete cascade,
  criada_em timestamptz not null default now(),
  primary key (usuario_a, usuario_b),
  check (usuario_a < usuario_b)
);
```

```typescript
// packages/protocolo/src/modelos.ts
export interface Amizade { usuarioA: string; usuarioB: string; criadaEm: string }
export interface PedidoAmizade { id: string; de: string; para: string; status: "pendente" | "recusado"; criadoEm: string }
```

### Regras

- **Pedir** (`de`, `para`): `de = para` dá `ErroApp("amizade_consigo")`; `para` inexistente dá `usuario_nao_encontrado` (404). Já amigos: nada muda, devolve `"amigos"`. Pedido de `para` para `de` pendente: apaga esse pedido e cria a amizade, devolve `"amigos"` (front-end spec: pedido cruzado vira aceite direto **[confirmado]**). Senão, cria o pedido pendente, ou devolve o que já existe (sem duplicar, AC 5); um pedido recusado volta a pendente. Devolve `"pedido_enviado"`.
- **Aceitar** (`pedidoId`, `eu`): só pedido pendente com `para = eu` (senão `pedido_nao_encontrado`, 404). Apaga o pedido, apaga um pedido no sentido contrário se houver (pedidos cruzados ao mesmo tempo) e cria a amizade com o par em ordem (`usuario_a < usuario_b`).
- **Recusar** (`pedidoId`, `eu`): só pendente com `para = eu`; vira `recusado`. Some da lista de quem recebeu e da de enviados de quem pediu (fluxo "Adicionar um amigo": "Pedido some de Enviados").
- **Recusar não bloqueia:** quem pediu pode pedir de novo, e o mesmo registro volta a pendente. Decisão desta story, para não deixar ninguém preso por um clique errado; bloqueio fica para quando houver abuso. Anotar em `docs/decisoes.md`.
- **Desfazer** (`eu`, `amigoId`): qualquer um dos dois (AC 4); sem amizade, `nao_sao_amigos` (404).
- **Buscar** (`login`): exato, sem diferença de maiúscula, aceita `@` no começo; valida o formato do GitHub (1 a 39 caracteres, letras, números e hífen, sem hífen nas pontas nem duplo). **Sem busca por prefixo:** por prefixo, digitar uma letra listaria quem usa o app. Cada resultado vem com a relação: `eu`, `amigo`, `pedido_enviado`, `pedido_recebido` (com o id, para aceitar ali mesmo) ou `nenhuma`.
- **Escrita atômica sem transação:** o modelo pede que aceitar apague o pedido e crie a amizade "na mesma transação". Com o `neon-http`, cada operação de mais de um passo é **uma instrução SQL só**, com CTEs que alteram dados (`with apagado as (delete ... returning ...) insert ...`): o Postgres executa a instrução inteira ou nada. Nada de duas chamadas seguidas ao banco para uma regra.
- As regras recebem o banco por parâmetro (tipo `PgDatabase` do Drizzle) e não sabem de sessão nem de Next; a Server Action resolve quem é `eu`.
- **Diferença da arquitetura:** o exemplo de `frontend-architecture.md` pede amizade por `paraLogin`; aqui o pedido vai pelo id que veio da busca, porque `login` não é único. A busca continua pelo login (AC 1).

### Server Actions

[Source: architecture/api-specification.md (Server Actions para amigos), architecture/frontend-architecture.md#service-example, architecture/error-handling-strategy.md]

```typescript
// apps/web/src/servidor/acoes/amizade.ts
"use server";
export async function pedirAmizade(paraId: string): Promise<Resultado<"pedido_enviado" | "amigos">> {
  return executar(async () => {
    const eu = await exigirSessao();
    const resultado = await regras.pedirAmizade(db(), eu.id, z.string().min(1).parse(paraId));
    revalidatePath("/amigos");
    return resultado;
  });
}
```

- Server Actions são endpoints públicos: cada uma confere a sessão e valida a entrada; o id de quem age vem sempre da sessão.
- Devolvem `Resultado<T>`, não lançam para a página. Entrada inválida vira `entrada_invalida`.

### Segurança

- Aceitar e recusar filtram por `para = eu` na própria instrução SQL; desfazer usa o par `(eu, amigoId)`. Um id de pedido de outra pessoa dá 404, sem dizer se existe.
- A busca só devolve id, login, nome e foto (os mesmos dados públicos do GitHub), nunca e-mail.
