## Story

**As a** criador,
**I want** criar uma jam a partir de um repositório meu do GitHub,
**so that** a gente trabalhe num projeto que já existe.

## Acceptance Criteria

1. A tela de nova jam lista os repositórios do usuário, com busca (FR4).
2. Escolher um repositório cria a jam com nome, repositório e criador.
3. A jam aparece no Início do criador (FR7).

## Escopo, dependências e riscos

**Entra:** tabelas `jam` e `participante` (migração 0003); lista dos repositórios próprios do usuário com busca; criar a jam com o commit de partida da branch padrão; o criador entra como participante; Início com as jams de que a pessoa participa (repositório, fotos dos participantes), abertas primeiro; "Criar jam" no Início leva à tela nova.

**Fica de fora:** criar repositório novo (2.2); chamar amigos (2.3, a tela de nova jam ganha a seleção lá); página da jam (2.4: até lá, criar a jam volta ao Início com ela em destaque); status do Claude no Início (Epic 4); tabela `fechamento` (Epic 5).

**Depende de:** Story 1.2 (token do GitHub com Metadata read e a instalação em "All repositories").

**Complexidade:** média.

**Riscos:** (1) repositório vazio não tem commit de partida (erro claro, com a sugestão de criar repositório novo pela jam na 2.2); (2) repositório que a instalação do GitHub App não cobre não aparece na lista (com "All repositories", todos aparecem); (3) conta com muitos repositórios (paginação).

**Pronto quando:** os 3 ACs cobertos por testes (regras contra PGlite com GitHub simulado, componentes, E2E sem sessão), migração no Neon, deploy no ar, e lint, tipos e testes passando.

### Modelo de dados

[Source: architecture/data-models.md#jam, #participante; architecture/database-schema.md]

```sql
create table jam (
  id text primary key,
  nome text not null,
  repo_owner text not null,
  repo_nome text not null,
  branch text not null,
  criador_id text not null references "user"(id),
  estado text not null default 'aberta' check (estado in ('aberta','fechando','fechada')),
  base_sha text not null,
  primeira_mudanca_em timestamptz,
  ultimo_commit_em timestamptz,
  criada_em timestamptz not null default now()
);
create table participante (
  jam_id text not null references jam(id) on delete cascade,
  usuario_id text not null references "user"(id) on delete cascade,
  papel text not null check (papel in ('criador','convidado')),
  colaborador text not null default 'pendente' check (colaborador in ('ok','pendente','falhou')),
  entrou_em timestamptz not null default now(),
  primary key (jam_id, usuario_id)
);
```

- Id da jam: "k7m2-rbq9", 8 caracteres de um alfabeto sem ambíguos (sem 0, o, 1, l, i), em dois grupos; usado no comando `npx` (Story 3.1). Colisão: tentar de novo com outro id.
- O criador entra como participante com `papel = 'criador'` e `colaborador = 'ok'` (é o dono do repositório).
- `nome` da jam = nome do repositório.

### Regras

- **Repositório próprio (D4):** só repositórios cujo dono é a conta do criador (`affiliation=owner` em `GET /user/repos`); ao criar, `GET /repos/{owner}/{repo}` confere de novo e o `owner.id` tem de ser o `githubId` de quem cria. Nome vindo do navegador nunca basta.
- **Commit de partida:** `default_branch` do repositório e `GET /repos/{owner}/{repo}/git/ref/heads/{branch}` → `object.sha`. Repositório vazio (409 do GitHub): `ErroApp("repositorio_vazio")` com a mensagem "Esse repositório ainda não tem nenhum commit. Faça um commit nele ou crie um repositório novo pela jam."
- **Uma jam aberta por repositório (decisão desta story, A11):** com uma jam não fechada no mesmo repositório, criar outra dá `jam_ja_existe` e mostra o link da existente (a jam fechada volta pela Story 5.2). Garantido por índice único parcial, não só pela regra.
- **Início (FR7):** jams de que a pessoa participa; abertas primeiro, depois as fechadas; cada uma com `dono/repositório` e as fotos dos participantes.
