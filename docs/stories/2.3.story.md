## Story

**As a** criador,
**I want** chamar até dois amigos para a jam,
**so that** eles tenham acesso ao repositório e entrem na sala.

## Acceptance Criteria

1. Só amigos aparecem para chamar; no máximo 2 (FR5, FR6).
2. Cada chamado vira colaborador do repositório e o convite do GitHub é
   aceito automaticamente em nome dele.
3. A jam aparece no Início de quem foi chamado.
4. Falha no GitHub (por exemplo, limite de colaboradores) mostra erro claro e
   não deixa o participante pela metade.

## Escopo, dependências e riscos

**Entra:** vaga do participante (1 a 3, única por jam) para o limite de 3 valer mesmo com pedidos ao mesmo tempo (A12, migração 0004); regra `chamarAmigo` (só o criador, só amigo, vaga livre); colaborador no GitHub com o token do criador e aceite do convite com o token do amigo; estado do colaborador (`ok`, `pendente`, `falhou`); seleção de amigos na nova jam ("0 de 2"); no Início, quem não foi adicionado aparece com "Tentar de novo" (para o criador) e, sem aceite automático, o link do convite (para o amigo).

**Fica de fora:** chamar mais amigos pela página da jam (2.4 traz a página; a ação reaproveita esta regra); sair da jam e remover participante; presença.

**Depende de:** Stories 1.3 (amizade), 2.1 e 2.2 (jam e criador participante).

**Complexidade:** alta.

**Riscos:** (1) **[verificar]** se o token de usuário do GitHub App aceita o convite (`PATCH /user/repository_invitations/{id}`); se não, o participante fica `pendente` e o amigo vê o link do convite para aceitar com um clique (external-apis.md); (2) o amigo pode não ter o app instalado ou ter o token vencido (cai no `pendente` com link); (3) só dá para provar de ponta a ponta com duas contas reais (o Lucas e o pai).

**Pronto quando:** os 4 ACs cobertos por testes (regras contra PGlite com GitHub simulado, componentes, E2E sem sessão), migração no Neon, deploy no ar, e lint, tipos e testes passando. A prova com duas contas fica anotada como ação do Lucas.

## Dev Notes

### Previous Story Insights

- A9: escrita de vários passos numa instrução SQL só; o `neon-http` não tem transação. A arquitetura previa `select ... for update` para o limite de 3, o que pediria o Pool por WebSocket. Com a vaga única (A12), o banco garante o limite sem transação.
- `gravarJam` (2.1 e 2.2) grava jam e criador numa instrução; o criador passa a ter `vaga = 1`.
- Amizade: `amizade` com o par em ordem pelo banco (`least`/`greatest`), ver `dominio/amizade.ts`.
- GitHub por interface pequena e adaptador em `servidor/github.ts`; `githubDoUsuario(id)` renova o token de qualquer usuário (o do amigo também).

### Vaga (A12)

```sql
alter table participante add column vaga smallint;
update participante set vaga = 1 where papel = 'criador';
-- convidados que existam ganham 2 e 3 pela ordem de entrada
alter table participante alter column vaga set not null;
alter table participante add constraint participante_vaga check (vaga between 1 and 3);
create unique index participante_jam_vaga on participante (jam_id, vaga);
```

Chamar: `insert ... select menor vaga livre` numa instrução; se outro pedido pegou a mesma vaga ao mesmo tempo, o índice recusa e a regra tenta de novo (até 3 vezes); sem vaga livre, `jam_cheia`.

### GitHub

[Source: architecture/external-apis.md]

- `PUT /repos/{owner}/{repo}/collaborators/{username}` com `permission: "push"`: 201 traz o convite (`id`, `html_url`); 204 quando já é colaborador.
- `GET /user/repository_invitations` (do amigo) e `PATCH /user/repository_invitations/{invitation_id}`: **[verificar]** com token de usuário do GitHub App. Sem aceite automático: `pendente` e o link `https://github.com/{owner}/{repo}/invitations` para o amigo.
- Erros comuns: 403 (sem permissão ou limite), 404 (repositório fora do alcance), 422 (usuário inválido).

### Interface

[Source: front-end-spec.md (Nova jam; fluxo "Criar uma jam")]

- Seleção de amigos com contador "0 de 2"; amigos são opcionais.
- Falha ao adicionar um colaborador: a jam é criada, o amigo fica "não adicionado" com botão de tentar de novo **[confirmado]**.
