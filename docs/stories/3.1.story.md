## Story

**As a** participante,
**I want** rodar um comando no terminal para ligar a pasta do projeto à jam,
**so that** meu PC passe a fazer parte da sala.

## Acceptance Criteria

1. `npx coodevelopment entrar <jam>` autentica o usuário sem token colado à
   mão (FR10): login por dispositivo, com código mostrado no terminal e
   confirmado em `/dispositivo` no navegador já logado.
2. Se a pasta do projeto não existe, o conector clona o repositório; se
   existe, confere que é o repositório da jam.
3. A página da jam mostra o participante como "conectado" enquanto o conector
   roda (FR8).
4. `npx coodevelopment diagnostico` diz o que está ligado e o que falta.
5. Funciona no Windows 10 e 11 (NFR4).

## Escopo, dependências e riscos

**Entra:**
- App: plugins `deviceAuthorization` e `bearer` do Better Auth; tela
  `/dispositivo` (confirmar ou recusar o código); `exigirSessao` aceita o
  Bearer do conector; `GET /api/jams/{id}/conector` (repositório e branch da
  jam, só para participante); `POST /api/conector/clone-token` (token de
  instalação do GitHub App, só leitura, só aquele repositório, 1 h, NFR8);
  `token-sala` emite `via: "conector"` quando a sessão vem do Bearer.
- Sala: a mensagem `presenca` ganha `conectados` (quem tem o conector ligado).
- Página da jam: selo "conectado" em cada participante com o conector ligado.
- Conector: `entrar`, `diagnostico` e `sair`; sessão guardada com DPAPI;
  clone ou conferência da pasta; conexão na sala com token renovado a cada
  reconexão; arquivo de descoberta da pasta (para os hooks do Epic 4).

**Fica de fora:** passo de conexão na página e ajuda para o Node (3.2);
sincronização de arquivos e vigia da pasta (3.3); instalar o plugin do Claude
Code e o servidor local dos hooks (Epic 4, Story 4.1); macOS e Linux.

**Depende de:** Stories 2.4 e 2.5 (sala e presença). A sala publicada na
Cloudflare (ação do Lucas na 2.5) só é necessária para conferir em produção;
o desenvolvimento e os testes usam a sala local (`wrangler dev`, sem conta).

**Ação do Lucas:** publicar `coodevelopment@0.1.0` no npm. O token de 7 dias da
1.1 já venceu; o caminho combinado é o trusted publishing pelo GitHub Actions
(ligar o repositório como publicador confiável no npmjs.com). Até lá, o
conector é testado com `node packages/conector/dist/cli.js`.

**Complexidade:** alta (primeiro código que roda no PC do usuário e grava no
disco; login por dispositivo; token do GitHub App).

**Riscos:**
1. **[verificar]** Token de instalação restrito a um repositório e a
   `contents: read` (`POST /app/installations/{id}/access_tokens` com
   `repository_ids` e `permissions`): conferir com um repositório privado.
2. **[verificar]** DPAPI sem dependência nativa: `ProtectedData` do .NET pelo
   PowerShell (`CurrentUser`), com o conteúdo pela entrada padrão, nunca na
   linha de comando.
3. O plugin `bearer` faz qualquer token de sessão valer como cabeçalho: o
   token do conector é uma sessão completa do usuário. Por isso ele nunca vai
   para log, para a URL nem para a linha de comando do git, e `sair` o revoga.
4. O `git clone` com token: passado por `GIT_ASKPASS` (ou cabeçalho por
   `-c http.extraHeader` em variável de ambiente), nunca gravado no
   `.git/config` nem no remoto.

**Pronto quando:** os 5 ACs cobertos por testes (unidade no conector, rotas e
tela no app, presença no workerd), CI verde no Windows, fluxo completo
conferido localmente (login, clone, "conectado" na página com a sala local), e
no ar adormecido em produção sem a sala.

## Tasks / Subtasks

- [ ] Task 1: Login por dispositivo no app (AC 1)
  - [ ] Plugins `deviceAuthorization` (`verificationUri: "/dispositivo"`, código de 10 minutos, intervalo de 5 s, `validateClient` só para o id do conector) e `bearer`; migração da tabela `device_code`
  - [ ] Tela `/dispositivo` em `(app)`: mostra o código vindo do link ou pede para digitar; Confirmar e Recusar; resultado na tela; axe sem violações em 1280 e 360 px
  - [ ] `exigirSessao` aceita `Authorization: Bearer`; rotas `/api` do conector respondem 401 em JSON (sem redirecionar para o login)
- [ ] Task 2: Rotas do conector (AC 2)
  - [ ] `GET /api/jams/[id]/conector`: `{ jamId, nome, repo: { owner, nome, id }, branch }`, 403 igual para quem não participa e para jam que não existe
  - [ ] `POST /api/conector/clone-token`: só participante de jam aberta; token de instalação do GitHub App (JWT do app com `GITHUB_APP_ID` e `GITHUB_APP_PRIVATE_KEY`) com `repository_ids: [repoId]` e `permissions: { contents: "read" }`
  - [ ] `token-sala` com `via: "conector"` quando a sessão vem do Bearer
- [ ] Task 3: Presença do conector (AC 3)
  - [ ] Protocolo: `presenca` com `conectados: [usuarioId]` (quem tem pelo menos uma conexão `via: "conector"`)
  - [ ] Sala: calcula `conectados`; testes no workerd
  - [ ] Página da jam: selo "conectado" no participante, atualizado sozinho
- [ ] Task 4: Conector, comando `entrar` (AC 1, 2, 5)
  - [ ] Endereço do app em `COODEVELOPMENT_URL` (padrão o de produção) para testar contra o local
  - [ ] Login por dispositivo: mostra o código e o link, abre o navegador, consulta a cada 5 s, respeita `slow_down`, `expired_token` e `access_denied`
  - [ ] Sessão em `%LOCALAPPDATA%\coodevelopment\sessao.bin`, cifrada com DPAPI; sessão vencida ou revogada (401) refaz o login
  - [ ] Pasta: sem repositório, clona `<pasta atual>\<nome do repo>` (ou a pasta atual se vazia); com repositório, confere o `origin` (dono e nome, ignorando `.git` e maiúsculas) e a branch; repositório diferente para com a explicação
  - [ ] Conecta na sala com `partysocket`, token novo a cada reconexão; mostra "Conectado à jam X" e segue rodando até Ctrl+C
  - [ ] Arquivo de descoberta `%LOCALAPPDATA%\coodevelopment\pastas\<sha1 do caminho>.json` com `{ jamId, pid }`, apagado ao sair
- [ ] Task 5: `diagnostico` e `sair` (AC 4)
  - [ ] `diagnostico`: Node (22+), git, sessão (válida, vencida, nenhuma), pasta atual (repositório e jam ligada), app acessível, sala acessível, Claude Code instalado (informativo); cada linha com o que fazer quando falta
  - [ ] `sair`: revoga a sessão no app e apaga o cofre local
- [ ] Task 6: Testes, CI e produção (AC 1 a 5)
  - [ ] Unidade no conector: argumentos, conferência do `origin`, consulta do login com os códigos de erro, cofre (DPAPI real só no Windows), diagnóstico
  - [ ] App: rotas novas (participante, não participante, Bearer, sem sessão) contra PGlite; tela `/dispositivo`
  - [ ] CI verde no Windows
  - [ ] Limite de taxa em `/api/auth/device/code` e `/api/auth/device/token` (o `rateLimit` do Better Auth por rota, ou regra no firewall da Vercel), como pede `security-and-performance.md`
  - [ ] Job de publicação do conector no CI por trusted publishing (OIDC, `npm publish --provenance`), disparado por tag `conector-v*`; sem o publicador confiável ligado no npmjs.com, o job falha só na publicação
  - [ ] Conferência local de ponta a ponta: login pelo navegador, clone de um repositório privado, "conectado" na página com a sala local
  - [ ] No ar em produção (rotas e `/dispositivo`); o conector publicado no npm depois da ação do Lucas
